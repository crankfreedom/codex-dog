## 统一更新入口与权限

| operation | 权限 | 行为 |
|---|---|---|
| updates.status | read | 当前版本、固定仓库/通道、候选、artifact ID、操作状态及错误；不返回缓存路径或幂等键 |
| updates.check | read | 检查固定 beta 源，不自动下载或安装 |
| updates.download | app.manage | 固定 candidateId/expectedVersion，持久记录后返回 operationId |
| updates.install | app.manage | 固定 artifactId/expectedVersion、confirm=true，排队进入安装门禁 |

当前共 19 项公开操作；updates.configure 和通用 operations 查询仍未实现，更新操作结果通过 updates.status 核对。
未安装的开发模式只可读取不支持状态；check/download/install 不会冒充已可运行。
首次申请默认 read；需要更新管理时申请 app.manage，并在桌面明确勾选“允许下载和安装更新”。
该权限不同于 access.manage，也不授予消息发送或卡消费能力。
CLI/IPC/MCP 共同进入 HostRouter 和唯一 UpdateService，不在传输层复制更新流程。

~~~powershell
# CLI 路径替换为实际安装目录；profile 见 packages.json。
codex-dog.exe access request --client updater --input updater-client.json --profile G05_PROFILE --json
codex-dog.exe updates check --client updater --profile G05_PROFILE --json
codex-dog.exe updates download --client updater --profile G05_PROFILE --input download.json --idempotency-key download-001 --json
codex-dog.exe updates status --client updater --profile G05_PROFILE --json
codex-dog.exe updates install --client updater --profile G05_PROFILE --input install.json --idempotency-key install-001 --json
~~~

updater-client.json 示例：

~~~json
{"clientLabel":"updater","requestedScopes":["read","app.manage"]}
~~~

download.json 使用当前 candidateId 和 expectedVersion；install.json 使用当前 artifactId、expectedVersion 及 confirm=true。
所有变更必须有幂等键；同调用者/操作/键/参数返回原记录，改参数拒绝。
失败操作不自动重做；明确处理错误后使用新操作键重试，同键查询仍返回原结论。
accepted 只代表已排队，不能据此断言安装成功；重启后版本相符才置 succeeded。

## 来源、完整性与缓存

- GitHub 源固定为 crankfreedom/codex-dog，测试通道为 beta；不接受外部调用方提供任意 URL 或仓库。
- 只接受更高的 beta SemVer 候选，拒绝 stable/同版/降级，不在下载后静默切换目标。
- 文件名固定为 Codex-Dog-G05-VERSION-Setup.exe，候选绑定版本、SHA-512 和大小。
- NSIS 非差分默认清单可能无 size，打包后根据最终安装包补齐完整 beta.yml。
- 下载由 electron-updater 执行；下载前复核候选，下载后及安装前再次流式检查大小/哈希。
- 强制完整下载，不使用差分 blockmap；本阶段没有 blockmap 发布要求。
- 缓存按 profile 与 github/fixture 分离，报告记录真实传输字节，避免缓存命中冒充 GitHub 网络下载。
- 回环 HTTP 仅在独立测试包经显式 --g05-fixture-port=PORT 启用，地址固定 127.0.0.1，不是正式更新源。
- 所有下载/安装均显式触发；autoDownload=false、autoInstallOnAppQuit=false，正常退出不悄悄安装。

测试包没有 Windows 发布者签名；HTTPS 和哈希只验证传输与清单一致性，不能替代发布者认证。
不在客户端内置 PAT、上传令牌、密码或签名私钥。私有发行仓库认证不属于当前方案。

## 安装门禁与退出顺序

1. 先持久记录安装操作并返回 accepted，让发起操作的短命 CLI 有机会正常退出。
2. 按进程映像名筛选，再核对完整可执行路径，并尝试独占打开安装版 CLI；长期 MCP/CLI 占用时返回 CLI_IN_USE，保留旧程序，不结束占用者。
3. worker 通过固定内部操作创建 SQLite 一致备份，路径为 profile/update-backups/OPERATION_ID.sqlite。
4. 复核客户端授权、artifact 与哈希，记录 awaiting_restart。
5. 阻止新请求，撤除本实例端点，关闭管道宿主、worker 和授权提交；确认自建子进程实际结束。
6. 退出协调后再次校验安装包，紧接着复核授权，再启动固定 NSIS 原位安装并重新运行；不转发任意命令、URL、程序路径或 Shell。
7. 新版本加载原 profile，版本匹配后将安装记录标成功；保留原未决意图、held 槽位及计数，不重放。

NSIS customInit/customUnInit 也执行 CLI 文件守卫，避免绕过应用直接运行安装器时强杀占用者。
Windows 对 EXE 文件映射的占用通过实际安装版 MCP 验证，不能只用一个模拟布尔值作为证据。
实测长期 SEA MCP 运行时独占 File.Open 仍可能成功，不能单独用它证明文件可替换；进程路径检测和文件句柄检测必须同时保留。
NSIS 外层启动程序可能返回 0，即使内层守卫已经退出；阻断证据须同时检查守卫返回 73、安装版 CLI/主应用版本未变和原 MCP 仍存活。
不是所有文件替换都具有整目录事务性；不承诺断电后整个安装目录自动回滚。

## 失败恢复策略

| 失败 | 处理与可核对结果 |
|---|---|
| GitHub/网络/限流/附件缺失 | 返回明确来源错误；不自动换镜像，不影响已运行模拟业务 |
| 下载损坏或缓存安装包被篡改 | 完整性失败，不运行安装器；可重新下载或修复后明确重试 |
| CLI/MCP 长期占用 | 安装器和统一入口均阻断；关闭占用者后用新操作重试 |
| 备份或退出门禁失败 | 不宣称安装成功，保留失败/待核对记录；不强杀其他应用 |
| 提交安装后仍启动旧版 | 标 INSTALL_NOT_APPLIED，不自动再次安装或降级 |
| 接受/执行中异常退出 | 标 OPERATION_INTERRUPTED，不在启动时重放下载或安装 |
| 新版正常/异常退出 | 延续既有子进程清理；用户手动恢复时重新核对版本与持久状态 |

updates.json 是独立技术记录，不把更新服务放进业务数据库写入路径；Schema 2 业务库继续由 worker 独占。
测试不修改旧 codex-resume 数据、真实目标锁、Codex 认证或 Goal 源库。
