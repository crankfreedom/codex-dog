# 备份与故障恢复

## 范围与数据位置

- 本手册对应 REQ-20261117-05。业务数据库由当前应用的 worker 唯一写入，外部 CLI/MCP 不直接读写数据库。
- 当前用户数据位于 `%LOCALAPPDATA%/codex-dog/profiles/<profile>/`。默认开发 profile 为 g02；Preview、Beta、Stable 的身份和 profile 互相区分，以实际启动入口和发行清单为准。
- 在应用运行时可通过桌面「打开本应用数据目录」，或具备 app.manage 的客户端执行 `desktop open-data-directory` 打开固定目录。该能力不接受任意路径。
- `codex-dog.sqlite` 保存本应用业务真值；同名 `-wal`/`-shm` 可能同时存在。`access.json`、客户端凭据、`source.json`、`updates.json` 和 Electron 缓存各有职责，不能用业务库备份冒充整个 profile 备份。
- 本应用不迁移旧产品数据。恢复时不得选择旧项目的数据库、作业、锁目录或授权文件，也不要修改 Codex 的认证和 Goal 源库。
- 备份可能包含本应用提示词、客户端秘密和授权。只保存在当前用户可控制的位置，提交故障报告时仅提供脱敏诊断和操作 ID，不上传整个 profile。

## 先停止写入，再人工备份

1. 先记录当前 profile、应用版本、API/Schema、出现的问题和相关任务/attempt/预约/更新操作 ID。可从页面、`app status`、`app version` 和本应用诊断读取；不要打开或输出凭据内容。
2. 有更新进行中时先查看其持久状态。`accepted`、断连或安装器退出码本身都不能证明安装完成；`awaiting_restart` 必须在重新启动后核对实际版本。
3. 从托盘明确选择「退出并停止监控」，或在桌面确认退出。**关闭主窗口仅隐藏驻托盘，不会停止数据库写入。**
4. 等待本实例退出。原 profile 的 CLI 应返回 APP_NOT_RUNNING，端点和本实例的 worker/管道宿主应清理；客户端不会自动拉起应用。若仍能查询，说明尚未完全停止，不能按静态文件方式备份。
5. 确认没有该 profile 的应用实例和自有子进程后，将整个 profile 复制到一个新的备份目录，保留原文件名和目录结构；存在的 SQLite 主文件、`-wal`、`-shm` 必须作为同组保留。不要只复制主文件，不要删除 WAL 来“修复”数据库。
6. 保留原现场和备份，记录复制时间与应用版本。备份操作不是远端业务撤销，恢复后仍须核对真实消息和卡消费事实。

当前没有公开的通用 `backup`/`restore` CLI、任意文件路径能力或 SQL 透传。上述是停止应用后的人工文件备份，不要编造相应命令。

## 更新前的一致数据库备份

更新服务在安装门禁内调用 worker 的固定内部操作；worker 停止新投递、等待本地在途落定后，通过 SQLite `VACUUM INTO` 创建一致数据库副本，包含已提交但尚未 checkpoint 的 WAL 真值。

备份写入当前 profile 的 `update-backups/<安装操作ID>.sqlite`；先写临时文件、校验完整性并同步，再排他发布，不覆盖已有目标。备份失败时拒绝安装并保留错误，不用复制运行中的主文件作为替代。

此备份覆盖本应用业务库，不含全部技术授权、来源配置和更新缓存。安装前后应保留原 profile 的其余文件，并在恢复时同时核对 `updates.json` 中的安装操作和实际应用版本。

更新不会自动回滚，也不保证断电时整个安装目录具有事务性。下载成功、哈希相符或 NSIS 外层退出码为 0 都不等于新版本已生效。

## 从备份核查和恢复

1. 完全停止应用，按上一节先保留当前现场的完整副本。不要覆盖唯一一份数据库、未决记录或更新操作文件。
2. 确认备份来自同一个 Codex Dog profile、当前 Windows 用户和相容版本。未知高版本、其他应用数据库或完整性损坏会被拒绝；不要修改 user_version、删除表或回填空库绕过检查。
3. 优先将备份复制到新的隔离 profile 中核查，而不是立即替换正在使用的数据。隔离核查入口必须显式使用 `--source=fixture`，避免连接真实卡片来源或推进真实业务；这只验证本机结构，不证明任何真实远端结果。
4. 若使用更新生成的单文件一致备份，将它作为隔离 profile 的 `codex-dog.sqlite`；不要把其他数据库残留的 WAL/SHM 与它混用。旧文件必须先作为原现场保留在独立目录，不能直接丢弃。
5. 首次启动后先只读查看诊断、任务、投递、预约和操作状态；暂停恢复出的任务，取消尚未领取且不再需要的预约。备份中的启用标志和授权不会因为“恢复”自动失效，不能把恢复当作安全暂停。
6. 对照当前现场与备份时间之后可能发生的真实副作用。若旧备份没有最新发送/消费意图，直接投入真实运行可能丢失防重依据；无法确认时保持隔离和暂停，保留两份数据，不重建任务、重置次数或换卡重试。
7. 只有数据库一致性、版本相容性和所有可能的远端副作用都核对清楚后，才人工决定将何份数据恢复到原 profile。恢复原 profile 同样必须先停止应用，完整保留原文件组，并再次显式选择来源；当前没有自动合并两份业务库的功能。

本手册不承诺从任意旧备份安全续跑，也不把 fixture 的成功当成真实状态已恢复。当前真实发送门禁和可信签名正例仍未完成，详见 [阶段 4](stage4.md)、[阶段 5](stage5.md) 和 [G06](g06.md)。

## 未决发送的处理

- `prepared`/`dispatching` 在崩溃后保守进入 uncertain；原 marker、计数、held 槽和目标锁身份保留。超时、断连、休眠或重启都不证明未发送。
- 先暂停后续任务，然后使用页面「仅核对原投递」或 `attempts reconcile`/`tasks reconcile` 核对原意图；通过配套 CLI 的 `--input`、原资源 ID 和新的核对操作幂等键提交。核对不发送新的消息。
- 提交、唯一回执、对应轮次结束和 Goal 最终完成是不同事实。未匹配原回执或未确认对应终态时，held 继续保留；不要编辑、删除、重建、切换模式、清理记录或直接改库绕过。
- 发现兼容目标锁冲突时保留锁文件。不能仅凭“窗口关闭”或“PID 似乎不存在”删除锁；应用只在原意图已终结、持有者退出且 target/token/pid 身份匹配时受控清理自己记录的锁。
- 真实账号/Goal 绑定、无正文回执和真实旧锁目录未核对时，应保留 TARGET_BINDING_UNVERIFIED/TARGET_LOCK_UNVERIFIED 等阻断，不将模拟锁或回执报告当作真实放行依据。

## 未决卡消费和错过预约

- 先查看预约状态、指定 cardKey、时间和结果摘要。完整 creditId、账号摘要和原消费键属于内部业务真值，不需要在普通日志或故障报告中展开。
- pending 可明确取消；running/uncertain 不能冒充取消成功。错过预约会标 missed，不补用，不因为稍后恢复额度或重新启动而自动消费。
- uncertain 只能对同一预约执行「核对原消费」。操作必须明确确认底层核对可能完成原消费，并且始终使用原卡和原幂等键；没有授权时不要执行真实核对。
- 原账号或指定卡变化、断连或读不到可信明细时保持未决。不要换卡、换消费键、新建预约或删除旧记录来尝试“恢复”。同账号另一张已有预约也必须受未决阻断。
- 记录 reset、nothingToReset、noCredit、alreadyRedeemed 的实际结果；这些值不能互相替代。真实消费尚未验收，隔离进程模拟不代表真实卡已经使用或恢复。

## 常见故障处置

| 现象 | 可执行处理 | 保留的结果 |
|---|---|---|
| 应用尚未启动或明确退出 | 从已审阅安装入口手动启动正确 profile，再重新查询 | CLI/MCP 离线不自动拉起 |
| 额度、目标或卡片来源断连/未知 | 保留来源选择，查看诊断；在同一明确来源进行只读刷新 | 不猜账号、不切实例、不显示正常 |
| 授权撤销/到期 | 在桌面核对新申请和所需独立权限；旧授权不会自动扩权 | 不重置原业务意图或消费键 |
| source/access/updates 或业务配置损坏 | 停止应用、保留文件与现场备份，核对相容版本和可信备份 | 失败关闭，不回填默认或删文件求启动 |
| 更新下载失败、清单缺失、哈希不符 | 查看原操作错误；明确重新检查或下载固定候选 | 不运行损坏安装包，不私自换镜像 |
| CLI/MCP 占用安装文件 | 正常结束占用本安装目录的 CLI/MCP，再明确申请新的安装操作 | 不结束无关应用，不把守卫拒绝当安装成功 |
| 更新准备、备份或清理失败 | 查看持久错误和本机诊断；确认业务已恢复观察，再处理原因 | 不跳过门禁、不声称升级成功 |
| 重启后仍为旧版本 | 查询 updates.status 的 INSTALL_NOT_APPLIED/实际版本，明确处理安装失败 | 不自动重放安装，不自动降级 |
| 签名缺失、发布者/链/时间戳不符 | 保留拒绝结果，使用经审阅的 Preview 或等待可信签名产物 | 不以自签或匹配哈希替代可信签名正例 |

## 当前发行边界

正式图标与发行配置可独立准备；可信证书/服务、发布者和签名凭据未配置时，签名发行门禁继续阻断。不要把未签名 Preview 描述为可信签名正式版。

实际恢复和升级验收还须验证 Schema 11 的任务、未决投递、卡预约及原消费键完整保留，并观察无重放。最终包、清单、本机与 runner 证据分开登记；公开 stable 或新 Release 必须在这些材料可审阅后再明确批准。
