## 本机构建入口

~~~powershell
pnpm --dir codex-dog release:check
pnpm --dir codex-dog release:build
pnpm --dir codex-dog test:g06
pnpm --dir codex-dog check:release
~~~

默认 mode=preview、version=0.6.0-beta.1；可通过 DOG_RELEASE_MODE / DOG_RELEASE_VERSION 设置，版本必须严格符合通道。
preview 和 signed-beta 仅接受 X.Y.Z-beta.N；signed-stable 仅接受 X.Y.Z，同版、降级和跨通道候选拒绝。
signed-stable 只有本机构建配置入口，当前 Actions 不提供该选项，任何模式打包均固定 publish=never。
签名条件缺失时在打包之前返回 SIGNING_NOT_CONFIGURED，不能静默产出“未签名正式版”。
每次输出 release/g06/MODE/VERSION/RUN_ID/，artifacts/g06/package.json 记录实际安装包、版本、SHA-512、大小及 published=false。
Preview 删除打包器默认渠道清单，不生成可被正式客户端消费的 beta.yml/latest.yml。
安装版读取严格校验的 dog-distribution.json，不能由 CLI 指定更新仓库、URL、发布者或关闭签名。
旧 G05 配置格式仅为历史测试包兼容保留，不复用其未签名更新权限。

## Windows 签名方案

当前首先预留 electron-builder 26.18.0 原生 Azure 签名入口，采用 win.azureSignOptions；不使用 v27 的新配置语法。
Azure Artifact Signing 的可用地区、申请资格、身份验证和费用须开通前按官方信息核对；未代表用户选择或购买服务。
云端密钥不进入构建机和客户端。其他 CA/HSM 服务未来通过构建适配接入，当前没有已经验证的 USB/HSM 或 PFX 流程。

| 环境字段 | 用途与存放 |
|---|---|
| DOG_SIGNING_ENABLED | codex-dog-signing 环境变量，明确设 true 才启用 |
| DOG_PUBLISHER_NAME | 证书中的实际发布者名称；不能填写 GitHub 用户名冒充 |
| DOG_AZURE_ENDPOINT | 对应区域的 HTTPS codesigning.azure.net 端点 |
| DOG_AZURE_ACCOUNT | 实际签名账号名 |
| DOG_AZURE_CERTIFICATE_PROFILE | 实际证书配置名 |
| AZURE_TENANT_ID / AZURE_CLIENT_ID | 签名主体的真实租户及应用 ID，环境变量 |
| AZURE_CLIENT_SECRET | 仅签名 Environment Secret，不写入源码、文档、日志或客户端 |

当前入口采用 v26 已支持的 EnvironmentCredential 客户端凭据，不声称已实现 OIDC。
后续优先评估短时身份/OIDC；必须核实固定版本签名模块支持的凭据链并实跑，再替换长期凭据，不将 azure/login 成功等同于签名模块必然可认证。
权限仅限相应证书配置的签名角色，按需轮换与撤销；账号建立、授权和计费均待用户实际配置。
v26 的原生集成会安装 TrustedSigning PowerShell 模块（MinimumVersion 0.5.0，并非精确锁定）；完整签名验收时还须记录实际解析版本和服务行为，不能宣称全链路可重复构建。

签名构建开启 forceCodeSigning、signExecutable 和 verifyUpdateCodeSignature，文件/时间戳摘要使用 SHA256。
独立 SEA CLI 通过 afterPack 显式签名；主程序、安装器和内嵌卸载器走 builder 签名流程。
安装包最终哈希及渠道清单在签名完成后生成；额外用固定 PowerShell 脚本复核主程序、CLI、安装器，未通过即构建失败。
卸载器实际安装后的签名、云端签名成功、证书轮换和签名后的两版升级尚待服务开通后验证。
不使用临时自签证书冒充对外可信签名，不承诺签名后必然没有 SmartScreen 提示。

## 安装前签名门禁

packages/infrastructure/windows-signature.ts 只启动系统 PowerShell 与固定 verify-signature.ps1，无任意 Shell 透传。
Windows Get-AuthenticodeSignature 必须 Status=Valid，签名证书具有代码签名 EKU，发布者精确匹配，且存在时间戳证书；超时、离线验证失败或任一条件不符均拒绝。
签名版下载后及安装前进行哈希/大小复核，再复核签名；退出协调后、启动 NSIS 前还会再次验证签名和最终授权。
这是对自定义安装器启动路径的补充，不能只依赖打包配置中的 verifyUpdateCodeSignature。
失败为 UPDATE_SIGNATURE_INVALID，CLI 退出码 5；保持失败操作记录，不自动换源、降级或重试安装。
发布者名称随安装包固化，不允许普通客户端修改；后续更换发布者主体须设计迁移，不直接放宽名称白名单。

## GitHub Actions

仓库为公开 crankfreedom/codex-dog；实施前检查 Actions 已启用，但没有工作流、Environment 或 Secret。
初版工作流已由用户推送并实跑。用户随后明确授权 agent 提交推送修复，并撤销全局禁止 AI 执行 Git 的规则；只提交本项目本轮文件，不夹带根工作区其他改动。

| 文件 | 触发与产物 |
|---|---|
| .github/workflows/ci.yml | main push、pull_request 或手动；strict/构建、单元、边界、文档、发行策略、SEA、G03/G02 模拟回归 |
| .github/workflows/windows-build.yml | 仅 workflow_dispatch，默认 preview；可选 signed-beta，仅主仓库 main，产出 Actions artifact，不上传 Release |

共同使用 windows-2025、Node 26.7.0、pnpm 11.20.0、frozen lockfile；四个外部 Action 固定完整 SHA，checkout 不保留凭据。
Action 本身运行于 Node 24，与应用构建用 Node 26 和 Electron 内嵌 Node 分别记录，不能混为一谈。
工作流 contents 仅 read，无 id-token 或发布写权限，无 tag 自动触发和 stable 发布入口，构建产物保留 7 天。
手工输入经环境变量传入并由 SemVer/模式校验，不在 Shell 中拼接 GitHub 输入。
signed-beta 使用 codex-dog-signing Environment，先核对非空 required_reviewers 保护规则；缺失或无权读取时拒绝签名构建。
Azure Secret 仅签名构建步骤获取，Preview 不获取签名秘密；GitHub 可能自动生成引用的空环境，但这不代表审批保护存在，当前不代替用户配置或降低审批规则。
后续用户须配置该环境的审批人、仅 main 分支策略、签名变量/秘密，再启用签名开关；不能把 YAML 写了 environment 当作保护规则已经存在。

### 干净仓库的边界

旧目标锁四项互操作测试依赖用户本机明确存在的旧源码；GitHub 单仓库没有该目录。
缺失时四项明确 skip，CI 保留两个真实新版子进程竞争验证；本机有旧源码时仍执行四项原始互操作测试。
没有从旧项目复制业务代码进发行包或要求 CI 同时检出旧项目，不把协议夹具或 skip 当作原始旧版互操作通过。

### 显式运行时与进程环境

Electron 45 的安装包可能在首次导入时才下载二进制；pnpm install 成功不等于 dist 已存在。
新增 scripts/ensure-electron.mjs，显式运行固定版本原生安装器并检查 dist/version、path.txt 和 electron.exe；拒绝覆盖路径，保持原下载校验。
两个工作流在编译/GUI 测试前执行 install:electron，发行构建入口也自行确保就绪，不再依赖本机已有副本或首次导入的隐式行为。

本机进一步复现：PowerShell 7 经 Node 等中间进程启动 Windows PowerShell 5.1，继承的 PSModulePath 使 Security/Utility 解析到不兼容模块。
清理该子进程环境中的 PSModulePath 后，原生 Get-ExecutionPolicy、Add-Type 和 ConvertTo-Json 恢复。
项目自身的管道、占用检查、签名复核、测试探针统一清理该继承项；父进程及全局环境不变，执行策略/ACL/证书校验没有放宽。
NSIS 也只在自身进程清理该继承项，避免手动从 PowerShell 7 运行安装器时再次传入错误路径。
该模块继承问题已本机复现并修复；它不是唯一故障，远端进一步暴露了下述 ACL 及诊断对象问题。
依据：[Microsoft PSModulePath 与中间进程继承](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath?view=powershell-7.3)。

### 失败证据与复验

新增 windows-preflight.json，只含系统/Node/PowerShell 版本、交互会话布尔值/编号和策略名称，不含用户、SID 或密钥。
应用失败只发出白名单阶段码、错误码和整数错误详情；测试启动包装器仅解析这些字段，不保留原始 stderr 或请求内容。
firstWindow 失败时写 startup-g02/g03/g06.json；两个工作流都在失败时尝试上传限定证据，不因无产物将失败误报为成功。
首轮修复新增脱敏及真实 Windows PowerShell 兼容测试，88 项本机单元通过；后续补充对象提前退出及 ACL 别名测试后为 90 项。当前 G03/G02 的 12/20 组模拟回归通过。

### 远端进一步定位与通过证据

初版诊断包装器在 firstWindow 失败后再次调用 desktop.process()，此时 Playwright 对象已销毁，导致诊断本身报错；改为预先缓存 ChildProcess，并增加提前退出/脱敏回归测试。
有效启动证据随后定位到 pipe 阶段。本机重现内置管理员 SID 的 SDDL 别名 LA：原代码用字符串包含完整 SID 判断合法性，因而误拒绝合法 ACL。
改为在原生访问规则中按完整 SecurityIdentifier 比较实际允许主体、FullControl、网络身份拒绝及受保护 DACL；目录同样验证仅当前 SID，未增加其他主体或放宽权限。
AclSelfTest 只在内存构造别名及额外主体反例，不创建管理员账号、不修改实际权限；本机及远端测试均验证接受合法别名、拒绝额外允许主体。
